# Phase 1: ディスクとページ

> このドキュメントは Phase 1（`pkg/storage/`）を理解するための前提知識をまとめたもの。
> Phase 1 のコードを読む前に、これを読む。

Phase 1 は **データベースの本体ではなく、その下の土台**。
SQL もテーブルもまだ出てこない。「ディスクとどう付き合うか」だけを扱う。

---

## §1. データベースって、結局なに？

Excel のファイルを思い浮かべる。画面上は「表」だが、保存されるのは `.xlsx` という **1 個のファイル**。

MySQL も PostgreSQL も同じで、突き詰めると **ディスクの上にあるファイルを読み書きしているだけ**。

だから自作 DB の仕事は、実はたった 2 つしかない。

1. 表のデータを、**ファイルの何バイト目に、どういう順番で書くか**を決める
2. そのファイルから目的の行を、**なるべく少ない手間で見つける**

2 つめが **インデックス**の話。このプロジェクトの目的そのもの。

---

## §2. メモリとディスクは別物

コンピュータには記憶場所が 2 種類ある。

| | たとえ | 電源を切ると | 広さ | 速さ |
|---|---|---|---|---|
| **メモリ（RAM）** | 机の上 | **消える** | 狭い（16GB とか） | 速い |
| **ディスク（SSD）** | 倉庫 | **残る** | 広い（1TB とか） | 遅い |

プログラムで `x = 5` と書いたときの `x` は全部メモリの上にある。速くて便利。

しかしメモリは電源を切ると消える。
データベースは消えたら困るので、**倉庫（ディスク）に置かなければならない**。
Phase 1 の面倒ごとは、全部ここから始まる。

---

## §3. どれくらい遅いのか

| | 実際の時間 | **メモリを「1 秒」としたときの体感** |
|---|---|---|
| メモリを読む | 約 100 ナノ秒 | **1 秒** |
| SSD を読む | 約 100 マイクロ秒 | **約 17 分** |
| HDD を読む | 約 10 ミリ秒 | **約 28 時間** |

SSD ですら、「メモリに聞けば 1 秒で終わる話を、17 分かけて倉庫まで取りに行く」ほどの差がある。

ここからこの先ずっと効いてくる結論が出る。

> **データベースの性能の話は、ほぼ全部「倉庫に何回行ったか」の話。**
> CPU の計算の速さはほとんど関係ない。

実行計画を読むときの一番大事な視点がこれ。
`EXPLAIN` が見せているのは、突き詰めれば「**倉庫に何回行くつもりか**」という見積もり。

---

## §4. だから「ページ」という箱で運ぶ

倉庫に行くのに 17 分かかるなら、**ネジ 1 本だけ取ってくるのは馬鹿らしい**。
どうせ行くなら箱ごと持って帰る。

しかも実際、ディスクは「1 バイトだけ読む」ことが物理的にできない。
必ずある程度の塊単位でしか読み書きできない。

この塊が **ページ (page)**。

| DB | ページサイズ |
|---|---|
| minidb | **4KB** |
| SQLite | 4KB |
| PostgreSQL | 8KB |
| MySQL (InnoDB) | 16KB |

### ここから出る 3 つの性質

- **1 行だけ欲しくても、その行が入っている 4KB を丸ごと読む**
- だから「何行読んだか」より **「何ページ触ったか」が性能を決める**
- **同じページに入っている行は、ついでにタダで読める**

### 具体例：インデックスの正体

1 行 100 バイトのテーブルに 1 万行あるとする。

```
全体のサイズ  = 100 バイト × 10,000 行 = 1,000,000 バイト
必要なページ数 = 1,000,000 ÷ 4,096   ≒ 245 ページ
```

ここで「`id = 7777` の行が欲しい」となったとき：

| | 触るページ数 | 実行計画での名前 |
|---|---|---|
| **インデックスが無い** | どこにあるか分からないので **245 ページ全部読む** | `Seq Scan`（全表走査） |
| **インデックスがある** | **3〜4 ページ読むだけ**で見つかる | `Index Scan` |

**245 回 vs 4 回、約 60 倍の差。**

これがインデックスの正体。魔法ではなく、単に**倉庫に行く回数が減っているだけ**。

「なぜ 4 回で済むのか」は Phase 3（B+Tree）で作りながら理解する。

---

## §5. Phase 1 の 3 つのファイルの関係

まず**大事な誤解ポイント**から。3 つのファイルは「上下に積まれた 3 階建て」ではない。
**運ぶ係が 2 つと、中身の並べ方の決まりが 1 つ**という関係になっている。

```
   disk.go   ... 倉庫との出入り口     ┐
   buffer.go ... 机の上の置き場       ┘ 4KBの箱を「運ぶ・置いておく」係

   page.go   ... 4KBの箱の中身の並べ方の決まり
                 （運ばない。ディスクを一切触らない）
```

`page.go` はディスクにアクセスするコードを 1 行も持っていない。
ただの 4096 バイトの配列に対して「先頭 16 バイトはヘッダ」「次はスロット」と
**意味を与えているだけ**。定規のようなもの。

### 上から下への流れ

「users テーブルの 3 ページ目が見たい」という要求が来たとき：

```
  上位層（Phase 2以降: テーブル / B+Tree / 実行器）
       |
       |  「3ページ目ちょうだい」
       v
  +----------------------------------------------------+
  |  buffer.go   バッファプール = 机の上                  |
  |                                                    |
  |    机にもうある？                                    |
  |      YES -> そのまま渡す（倉庫に行かない。速い）       |
  |      NO  -> 下に頼む                                |
  +----------------------------------------------------+
       |
       |  「3ページ目を倉庫から取ってきて」
       v
  +----------------------------------------------------+
  |  disk.go     DiskManager = 倉庫の受付                |
  |                                                    |
  |    3 x 4096 = 12288 バイト目から 4096 バイト読む       |
  |    ReadCount を +1 する   <- 性能測定の要             |
  +----------------------------------------------------+
       |
       v
  data.db   [ページ0][ページ1][ページ2][ページ3][ページ4]...
                                        ^^^^^^ ここ
```

**上位層は `disk.go` を直接呼ばない。必ず `buffer.go` を通す。**
これが守られているから「同じページを 100 回見ても倉庫に行くのは 1 回」が成立する。

そして `page.go` は、この流れのどこにも登場しない。
運ばれてきた 4096 バイトを**解釈するとき**にだけ使われる。

## §6. スロット式ページ（`page.go`）

4KB の箱の中に、行をどう並べるか。

### まず空のページ

```
  0      16                                              4096
  |------|-------------------------------------------------|
  |header|                    free                         |
  |------|-------------------------------------------------|
         ^                                                 ^
     freeStart = 16                              freeEnd = 4096

  ヘッダ16B          空き領域 4080B
```

ヘッダには「このページの種類」「行が何個入っているか」「空き領域はどこからどこまでか」
といった管理情報が入っている。

### "alice"（5バイト）を入れる

```
  0      16    20                                  4091   4096
  |------|-----|-------------------------------------|-----|
  |header|Slot0|              free                   |alice|
  |------|-----|-------------------------------------|-----|
              ^                                      ^
        freeStart = 20                        freeEnd = 4091

  Slot0 = (offset=4091, length=5)
          「aliceは4091バイト目から5バイト分」という付箋
```

データは**後ろの端**に置き、「どこに置いたか」を書いた付箋（スロット）を**前から**足す。

### "bob"（3バイト）を追加

```
  0      16    20    24                       4088  4091   4096
  |------|-----|-----|---------------------------|-----|-----|
  |header|Slot0|Slot1|          free             | bob |alice|
  |------|-----|-----|---------------------------|-----|-----|
                    ^                            ^
              freeStart = 24                freeEnd = 4088

  Slot0 = (4091, 5)  -> alice
  Slot1 = (4088, 3)  -> bob

              ---->                        <----
         スロットは前から伸びる         データは後ろから伸びる
```

### なぜ両端から詰めるのか

「スロット用に先頭 1000 バイト、データ用に残り」と**固定で区切ったらどうなるか**を考える。

```
  ケースA: 大きい行が少数しか入らない場合

  |header|Slot0|      ここが全部無駄       |      大きい行1個      |
         <------- スロット領域 1000B ------>
         スロットは1個しか使わないのに1000B確保 -> 無駄


  ケースB: 小さい行がたくさん入る場合

  |header|Slot0|Slot1|...|Slot249| 満杯!! |小|小|小|  まだ空き   |
         <------- スロット領域 1000B ------>
         スロットが足りなくて入れられない。データ領域は余っているのに -> 無駄
```

**行のサイズは事前に分からない**（TEXT 列があれば行ごとに長さが違う）。
だから「どこで区切るか」を先に決められない。

両端から詰めれば、**境界は自動的に決まる**。
スロットとデータが出会った瞬間が、そのページの満杯。

```
  満杯の判定 = freeStart と freeEnd が出会ったとき

  |header|Slot0|Slot1|Slot2|Slot3|tupleD|tupleC|tupleB|tupleA|
                                 ^
                          freeStart == freeEnd
```

### なぜ「付箋」を経由するのか（RID の安定性）

ここが**インデックスにとって死活問題**になる部分。

行の住所は **RID = (ページ番号, スロット番号)** で表す。
インデックスはこの RID を指す。

```
  インデックス（B+Tree / Phase 3で作る）

     id=200  ------>  RID(ページ3, スロット1)
                              |
                              v
     ページ3 の Slot1 = (offset=4088, length=3)
                              |
                              v
                      4088バイト目の "bob"
```

ここで、ページ内を整理して "bob" を 4090 バイト目に動かしたとする。

```
  ページ3 の Slot1 = (offset=4090, length=3)   <- 付箋だけ書き換える

  インデックスは RID(ページ3, スロット1) のまま。書き換え不要。
```

**もし付箋が無く、インデックスが直接 4088 バイト目を指していたら**：

```
  インデックス

     id=200  ------>  ページ3の4088バイト目
                              |
                        行が動いた瞬間、この矢印は壊れる
                              |
                        全インデックスを書き換えないといけない
```

インデックスが 5 本、行が 100 万件あったら、行を 1 つ動かすたびに大惨事になる。
**付箋を 1 枚経由するだけで、この問題が消える。**

### 削除が「墓標」である理由

`bob` を削除する。

```
  削除前:  Slot1 = (4088, 3)
  削除後:  Slot1 = (0, 0)      <- length=0 が「ここは削除済み」の印（墓標）

  0      16    20    24                       4088  4091   4096
  |------|-----|-----|---------------------------|-----|-----|
  |header|Slot0|Slot1|          free             | bob |alice|
  |------|-----|-----|---------------------------|-----|-----|
                ^^^^^                            ^^^^^
              墓標にする                    この領域は回収しない
```

理由が 2 つある。

**理由1: 詰め直しが高価すぎる**

領域を回収するには、後ろのデータを全部ずらして、
ずれた分だけ**全スロットの offset を書き換える**必要がある。
削除のたびにこれをやっていたら遅くて使い物にならない。

**理由2: スロット番号がずれると、インデックスが静かに壊れる**

もしスロット配列から Slot1 を「詰めて」消したら：

```
  削除前:  Slot0=alice  Slot1=bob  Slot2=carol
  詰めると: Slot0=alice  Slot1=carol
                              ^^^^^
      インデックスが持つ RID(ページ3, スロット1) は
      bob を指していたはずが、黙って carol を指すようになる
```

**バグにすらならず、間違った行が返る。** これが一番怖い。
だから番号は絶対に詰めない。

この設計の結果が、実際の RDBMS で誰もが遭遇する挙動になる。

> **`DELETE` してもファイルサイズが小さくならない。**

領域の回収は、削除時ではなく後からまとめて行う
（PostgreSQL の `VACUUM`、ページ分割時のデフラグなど）。

## §7. バッファプール（`buffer.go`）

机の上をどう管理するか。

### 全体像

```
  バッファプール（フレーム4枚の例）

    フレーム0 : [ページ7のコピー]   pin=0   dirty=false
    フレーム1 : [ページ3のコピー]   pin=2   dirty=true
    フレーム2 : [ページ9のコピー]   pin=0   dirty=false
    フレーム3 : [    空き      ]

  ページ表（どのページがどのフレームにあるか）
    ページ7 -> フレーム0
    ページ3 -> フレーム1
    ページ9 -> フレーム2
```

- **フレーム** = 机の上の 1 区画。4KB ちょうど入る
- **pin** = いま何人が使用中か。1 以上なら捨てられない
- **dirty** = 書き換えられたか。true なら捨てる前に倉庫へ書き戻す必要がある

### pin / unpin：使用中のページを守る

```
  FetchPage(3)   -> pin=1    「使うから捨てないで」
  FetchPage(3)   -> pin=2    「別の処理も使い始めた」
  UnpinPage(3)   -> pin=1    「1人終わった」
  UnpinPage(3)   -> pin=0    「もう誰も使ってない = 捨ててOK」
```

**なぜ必要か。pin が無い世界で何が起きるか：**

```
  あなた  : p = FetchPage(3)      p はフレーム1 を指す
                                  |
  別の処理: NewPage() したい      |
            机が満杯 -> フレーム1 を追い出す
            フレーム1 を ページ12 に使い回す
                                  |
  あなた  : p.Get(0)   <- ページ12 の中身を読んでしまう！
```

`p` はただのメモリへのポインタなので、**中身がすり替わっても気づけない**。
静かにデータが壊れる。pin はこれを防ぐための「使用中」の札。

だから `unpin` を忘れると、そのフレームは永久に居座る（buffer leak）。
本物の RDBMS でも実際に起きるバグ。

### LRU：机が満杯のとき、どれを戻すか

**LRU = Least Recently Used = 一番長く使っていないもの**を追い出す。

```
  LRU の列（pin=0 のフレームだけが並ぶ）

    古い  <-------------------------->  新しい
    [フレーム2]        [フレーム0]
        ^
    次に追い出される

  フレーム1 は pin=2 なので、この列に並んでいない = 追い出し候補にならない
```

「最近使ったものは、また使う可能性が高い」という経験則に賭けている。
実際、B+Tree の根ノードは全検索が必ず通るので、常にこの列の右端にいる。

### 遅延書き込み（dirty）：書き換えてもすぐ倉庫に戻さない

ページ3 を 10 回書き換えた場合を比べる。

```
  もし毎回ディスクに書いたら          minidb（dirty フラグ）
  ------------------------          --------------------------
  書き換え -> 倉庫へ (17分)          書き換え -> dirty=true にするだけ
  書き換え -> 倉庫へ (17分)          書き換え -> もう dirty なので何もしない
  書き換え -> 倉庫へ (17分)          書き換え -> 同上
       ... x10                            ... x10
                                    追い出される時に 1 回だけ書く
  = 倉庫まで 10 往復                 = 倉庫まで 1 往復
```

10 回分の更新が 1 回の物理書き込みにまとまる。

（その代わり、書き戻す前に電源が落ちるとデータが消える。
本物の RDBMS はこれを WAL で解決する。minidb では割り切っている。）

### そして全部が繋がる：なぜ Index Scan が速いのか

Phase 3 で作る B+Tree を、バッファプールの視点から見ると：

```
              [根ノード]           <- 全ての検索が必ず通る
              /    |    \             = 常に机の上（バッファヒット・倉庫行き0回）
        [中間] [中間] [中間]        <- よく通る
         / | \                        = だいたい机の上
    [葉][葉][葉][葉][葉]            <- 目的の1枚だけ倉庫から取ってくる

  木の高さが3でも、実際に倉庫へ行くのは 1〜2 回
```

一方 Seq Scan は、245 ページを全部倉庫から取ってくる。しかも一度使ったら二度と使わないので、
バッファに載せても他の有用なページを追い出すだけで意味がない。

**`EXPLAIN ANALYZE` が最終的に見せる数字（hit / miss / read）は、この差そのもの。**

## 用語まとめ

| 用語 | 意味 |
|---|---|
| **ページ (page)** | ディスクとの読み書きの最小単位。minidb では 4KB |
| **PageID** | ファイル先頭から何番目のページか。バイト位置 = PageID x 4096 |
| **タプル (tuple)** | 1 行のデータ。ページの中に詰められる |
| **スロット (slot)** | 「このタプルはページ内の何バイト目から何バイト」を書いた付箋 |
| **RID** | 行の住所 = (PageID, SlotID)。インデックスが指すのはこれ |
| **墓標 (tombstone)** | 削除済みの印（length=0）。領域は回収しない |
| **フレーム (frame)** | バッファプール内の 1 区画。ページ 1 枚分 |
| **pin / unpin** | 使用中の札。pin>0 の間は追い出されない |
| **dirty** | 書き換え済みの印。追い出す前に倉庫へ書き戻す必要がある |
| **LRU** | 一番長く使っていないものから追い出す方式 |
| **バッファヒット** | 欲しいページが既に机の上にあった = 倉庫に行かずに済んだ |
| **Seq Scan** | 全ページを頭から読む実行計画。インデックスが無いときの手段 |
| **Index Scan** | インデックスを辿って必要なページだけ読む実行計画 |
