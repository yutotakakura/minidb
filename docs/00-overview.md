# minidb — 全体像とロードマップ

## このプロジェクトの目的

**実行計画（EXPLAIN）とインデックスを、原理から理解すること。**

RDBMS を「使う」立場だと、`EXPLAIN` の出力は呪文に見える。
`Seq Scan` と `Index Scan` のどちらが選ばれるのか、`cost=0.00..35.50` の数字は何なのか、
なぜインデックスを貼ると速くなり、なぜ時々貼っても使われないのか。

これらは全部、内部を一度作ってしまえば当たり前の話になる。
だから作る。**性能を出すためではなく、見えるようにするために作る。**

そのため minidb は、普通の DB なら隠す情報をあえて全部表に出す。
特に **触ったページ数**（＝ディスクに何回行ったか）を常に数えていて、
`EXPLAIN ANALYZE` がそれをそのまま表示する。

## 完成したときのイメージ

```sql
minidb> EXPLAIN ANALYZE SELECT name FROM users WHERE id = 7777;

Projection (name)
  -> Index Scan using users_id_idx on users  (cond: id = 7777)
       rows=1  pages read=4  buffer hit=3 miss=1

-- 同じクエリを、インデックスを消してから実行すると:

Projection (name)
  -> Seq Scan on users  (filter: id = 7777)
       rows=1  pages read=245  buffer hit=0 miss=245
```

**245 ページ vs 4 ページ。** この数字の差を自分の手で作り出せるようになるのがゴール。

## 全体アーキテクチャ

上から下へ、SQL 文字列が結果に変わるまでの流れ。
左の数字は、それを作る Phase。

```
                 SELECT name FROM users WHERE id = 7777
                                 |
   Phase 4       レキサ → パーサ  |
                                 v
                       AST（構文木・ただの構造体）
                                 |
   Phase 5       プランナ         |
                                 v
                 論理プラン ──> オプティマイザ ──> 物理プラン
                 「何をするか」   「どうやるか決める」  「Index Scan を使う」
                                 |                  ← 実行計画が決まるのはここ
   Phase 6       実行器           |
                                 v
                    イテレータの木（Volcano モデル）
                                 |
                                 v
   Phase 2/3     ヒープファイル（全表走査）  /  B+Tree（インデックス）
                                 |
                                 v
   Phase 1       バッファプール（メモリ上のページ置き場・I/O 計測）
                                 |
                                 v
   Phase 1       DiskManager（ページ単位の読み書きだけを担当）
                                 |
                                 v
                       data.db（4KB ページがひたすら並んだ 1 個のファイル）
```

重要なのは **下の層ほど「遅くて確実」、上の層ほど「賢いが実体を持たない」** ということ。
最下層の `data.db` だけが本物のデータで、上は全部それをどう触るかの工夫でしかない。

## Phase ロードマップ

| Phase | 内容 | 得られる理解 | 状態 |
|---|---|---|---|
| 1 | スロット式ページ / DiskManager / バッファプール | ディスクとメモリの境界 | 実装済み |
| 2 | スキーマ・タプル符号化 / ヒープファイル / 全表走査 | Seq Scan の実体 | 着手中 |
| 3 | B+Tree インデックス | インデックスの構造と木の高さ | 未着手 |
| 4 | SQL レキサ / パーサ → AST | 文字列から構文木へ | 未着手 |
| 5 | 論理プラン → オプティマイザ → 物理プラン | **実行計画が選ばれる仕組み** | 未着手 |
| 6 | Volcano イテレータ実行器 | プランが動く仕組み | 未着手 |
| 7 | `EXPLAIN` / `EXPLAIN ANALYZE`（ページ I/O 数付き） | **本命** | 未着手 |
| 8 | REPL | 触って確かめる | 未着手 |

Phase 5 と 7 が目的そのもの。1〜4 はそこに辿り着くための土台。

## なぜ Go か

- **バイト列を明示的に扱える。** `encoding/binary` で 4KB のページを自分で設計した通りに詰められる。
  ディスク上のレイアウトを自分で決めた実感が残る。
- **GC があるので所有権と戦わない。** バッファプールは「ページを貸し出す」構造で、
  B+Tree は親子ノードを行き来する。Rust だとここが最大の難所になり、
  *DB を理解する時間より借用検査と戦う時間が長くなる*。
- **後半のトランザクションが素直。** ロックや MVCC に進むとき goroutine と `sync` がそのまま使える。
- **計測が標準装備。** `go test -bench` で「インデックスあり/なしのページ読み込み回数」を数字で出せる。
- **キャリア面。** バックエンド／インフラの事実上の標準で、DB 系 OSS も Go が多い
  （TiDB, CockroachDB, Dolt, InfluxDB）。この自作 DB がそのまま OSS を読む土台になる。

将来 Rust で書き直すと、ストレージ層の理解はさらに深まる。ただし順番として Go が先。

## 進め方

**1 フェーズずつ区切る。** 実装 → テスト → 設計判断の解説 → 次へ。
理解が目的なので、動くコードより「なぜそう作ったか」を残すことを優先する。

各 Phase の解説は `docs/` に番号付きで残していく。

## 動かし方

```bash
cd ~/dev/minidb
go test ./... -v
```

## 意図的に作らないもの

学習の焦点をぼかさないため、以下は割り切っている。実際の RDBMS との差として覚えておく。

| 割り切り | 本物ではどうなっているか |
|---|---|
| 削除しても領域を回収しない | `VACUUM`（PostgreSQL）やページ分割時のデフラグで回収 |
| 空きページを再利用しない | Free Space Map で管理して再利用 |
| WAL・クラッシュ復旧が無い | WAL に先に書いてから本体を更新（Phase 外・余力があれば） |
| トランザクション・MVCC が無い | 同上 |
| 1 タプルが 1 ページに収まらないと失敗 | TOAST（PostgreSQL）やオーバーフローページ（SQLite）に追い出す |
